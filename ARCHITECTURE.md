# Architecture decisions

## Wallet creation and money (Stage 3)

- `Money` is a domain value object backed by `decimal.js`. It accepts decimal strings, enforces a three-letter currency and at most two fractional digits, is frozen at runtime, and serializes to fixed-scale strings. Monetary values never pass through JavaScript `number`.
- Wallet balances are stored as PostgreSQL `NUMERIC(18,2)` and UUIDv7 values are generated by the application. The HTTP boundary validates the request before the use case constructs domain values.
- `CreateWalletUseCase` owns wallet-opening rules. The wallet module's persistence port keeps MikroORM out of the domain and application policy. The MikroORM adapter persists the wallet and, for positive opening balances, the internal `OPENING` transaction and its credit ledger entry in one `EntityManager.transactional` call.
- A zero opening balance creates a wallet without a transaction or ledger entry. Duplicate `(playerId, currency)` wallets are reported as a conflict. Database constraints remain the final authority for uniqueness and financial invariants.
- `OPENING` is created only by the wallet-opening domain flow; it is excluded from external transaction kinds.

Authentication remains outside this stage and is optional in the challenge. If introduced, it belongs at the HTTP boundary through a NestJS guard and an external identity provider; it must not add transport concerns to the domain.

## Wager processing and idempotency (Stage 4)

- `Idempotency-Key` is scoped by `(providerId, idempotencyKey)`. The SHA-256 hash is built from canonical JSON for `providerId`, `externalTransactionId`, `playerId`, `walletId`, `roundId`, `gameId`, `kind`, `money` and the optional `referenceExternalTransactionId`. Keys are sorted recursively; transport metadata is excluded.
- PostgreSQL uniqueness reserves both `(provider_id, idempotency_key)` and `(provider_id, external_transaction_id)`. The wager row is inserted inside the same transaction as the wallet lock and all financial writes. A concurrent unique-key loser reads the winner after its transaction rolls back: equal hash replays the stored status and balance, while a different hash returns a conflict.
- The processing unit locks the wallet with MikroORM `PESSIMISTIC_WRITE` inside `EntityManager.transactional()`. The domain wallet applies BET/WIN/LOSS behavior; the adapter persists wallet, terminal transaction result, optional ledger entry and integration events in the existing outbox atomically.
- `LOSS` and insufficient-funds rejections store the balance observed during processing and create no ledger entry. `version` only advances when a balance movement occurs. WIN references, when supplied, must identify a processed BET for the same provider, player, wallet, round and currency.
- The HTTP endpoint is introduced in this step to exercise the shared use case. Its complete provider-facing status contract remains part of Stage 6.

## SQS inbox processing (Stage 5)

- `WagerSqsConsumer` validates the queue envelope before constructing domain `Money`, then calls the same `ProcessWagerUseCase` used by HTTP.
- The inbox reservation uses `(consumer_name, message_id)` and is inserted on the transaction-scoped EntityManager before wager reservation. The inbox row, wallet mutation, transaction, ledger, and outbox therefore commit or roll back together. A duplicate delivery is acknowledged only after the first delivery has committed; the transaction commit itself marks the inbox row processed.
- Terminal wager rejections and duplicate deliveries are acknowledged. Invalid envelopes and inbox ID/hash conflicts are copied to the FIFO DLQ before the original is deleted. Other failures keep the message available with exponential visibility delay; the queue redrive policy sends repeated failures to the DLQ after three receives. Missing wager references currently follow this retry/DLQ path; persistent pending-reference recovery remains unimplemented.
- On shutdown, the poller stops receiving, finishes the current message, and returns unstarted messages from the received batch to the queue by setting their visibility to zero.

## Outbox publishing and HTTP result contract (Stage 6)

- `OutboxPublisher` claims due events in short PostgreSQL transactions using `FOR UPDATE SKIP LOCKED` and a 60-second lease. It publishes outside the claim transaction, then marks success or schedules exponential retry. A crash after publish can cause redelivery; `eventId` remains the SQS FIFO deduplication ID and is the consumer idempotency key.
- Events publish to `wager-events.fifo`, grouped by `aggregateId`. The queue URL is validated from configuration and the LocalStack initialization script provisions the queue.
- The synchronous wager endpoint returns `200` for processed/replayed processed transactions and `422` for persisted business rejections. Validation is `400`, idempotency/external transaction conflicts are `409`, and recognized temporary PostgreSQL connection/deadlock/lock-timeout errors are `503`. Internal errors stay sanitized as `500`.
- HTTP and SQS workers are composed by `AppModule` through `WagerWorkersModule`; feature tests can import `WagerModule` without starting background polling.

## Module layout

- Feature slices keep the NestJS entry points and related files together: `*.module.ts`, `*.controller.ts`, concrete `*.repository.ts`, `*.interface.ts`, `*.errors.ts`, `*.mappers.ts`, `dtos/`, and `entities/`.
- Use cases live in a direct `use-cases/` directory in each slice. Wager hashing lives in `wager.utils.ts` beside the wager module files.
- `WalletRepository` and `WagerRepository` are concrete MikroORM implementations in their owning slices. `WalletRepositoryInterface` and `WagerRepositoryInterface` live in the corresponding `.interface.ts` files and use Nest symbol tokens for dependency injection.
- `WagerRepository` also implements the transaction-scoped `WagerUnitOfWork` port. Each callback gets a fresh repository instance bound to MikroORM's transactional `EntityManager`, so the locked wallet and reserved wager state cannot leak across concurrent requests. The separate port remains the use case's transaction boundary contract; no second implementation class is needed.
- HTTP DTOs live under each slice's `dtos/`, one operation DTO per file; the reusable amount/currency transport shape is in `common/dtos/money.dto.ts`. Repository port contracts stay in `.interface.ts`, while use-case input and response contracts are colocated with the corresponding operation DTO.
- Errors owned by a slice are declared in its `*.errors.ts`; the pure domain may import these error types but does not depend on NestJS or MikroORM.
- MikroORM calls its mapped persistence classes entities and implements Data Mapper / Unit of Work patterns. Its documentation does not prescribe a directory convention or equate these classes with DDD entities. In this codebase, DDD models remain in `domain/`; MikroORM mappings remain in each slice's `entities/`, and mappers explicitly translate between them. The `.entity.ts` suffix refers to MikroORM persistence mappings; `Wallet`, `WagerTransaction`, and other domain types are business models. The wager persistence class uses `WagerTransactionOrmEntity` to make that distinction explicit in code.
- Slice-level `*.mappers.ts` files own non-trivial transformations between domain models, repository contracts and MikroORM entity data. Repositories still own query, transaction, locking and persistence orchestration.
- Wallet entities are owned by `modules/wallet/entities`; wager, inbox and outbox entities are owned by `modules/wager/entities`. Shared MikroORM configuration and versioned migrations remain in `infrastructure/persistence/`.
- Use case classes name each business operation. The wallet creation and wager processing flows do not need a generic service layer of their own.

## Error handling

- Domain and application errors extend the framework-independent `ApplicationError` base and expose a stable `code`; they do not contain HTTP status codes.
- The global NestJS HTTP exception filter maps known application error codes to HTTP statuses and a consistent `{ statusCode, code, message, timestamp }` response. The current mapping uses 400 for invalid input, 404 for missing resources, 409 for conflicts/state conflicts and 422 for business mismatches/rejections. These are API adapter decisions, not domain rules.
- Persistence mappers translate domain validation errors raised while rehydrating stored records into internal consistency errors, so corrupt database state is reported as a sanitized 500 rather than a client input error.
- The filter preserves NestJS `HttpException` status and safe response messages. Unexpected or unmapped errors return a generic 500 response; internal messages are not sent to clients. The filter is HTTP-only; SQS and workers retain their own retry/ack/DLQ error policies.
- Catch blocks remain only where code recovers, translates an infrastructure failure at an adapter boundary, or intentionally converts an exception into a business result. Controllers do not catch errors solely to map HTTP responses.
